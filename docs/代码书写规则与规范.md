# 代码书写规则与规范

> 适用于本队「安全智能运维 Agent」项目（Web + Agent + MCP + 可选多语言模块）。  
> 若某语言有更细子规范，可在 `docs/code-style/` 下增补并以本文件为总则。

---

## 1 总则

1. **可读性优先**：命名清晰、结构扁平有度、避免「聪明但难懂」的写法。  
2. **安全默认**：任何可能改系统的路径必须经过护栏；禁止在业务代码中写死 root 口令或 API Key。  
3. **可追溯**：关键路径打结构化日志，携带 `traceId` / `sessionId`。  
4. **与需求/设计一致**：模块名、接口与《软件功能需求分析文档》《软件功能设计文档》保持可追踪（可在 PR 或提交说明中引用章节号）。

---

## 2 仓库与目录结构

- **建议顶层目录**（可按技术栈调整，全队统一即可）：

  - `frontend/`：Web 前端  
  - `backend/`：HTTP/API、会话、审批、持久化  
  - `agent/`：编排、ReAct/Plan、与模型交互  
  - `mcp-servers/`：各 MCP Server（按域分子目录）  
  - `docs/`：需求、设计、规范、部署说明  
  - `deploy/`：脚本、systemd、Dockerfile（若有）  
  - `scripts/`：一次性工具脚本（不入生产依赖主路径）

- **禁止**将大体积模型权重、整库数据、含密钥的 `.env` 提交入库；使用 `.env.example` 列出键名与示例占位。

---

## 3 命名规范

| 对象 | 规则 | 示例 |
|------|------|------|
| 目录 | 小写短横线或小写单单词，全队统一一种 | `mcp-servers/system-info` |
| 后端类/类型 | 大驼峰 | `SecurityController` |
| 函数/方法 | 小驼峰（Java 则按语言习惯） | `evaluateRisk()` |
| 常量 | 全大写下划线 | `MAX_TOOL_TIMEOUT_MS` |
| MCP tool | 稳定英文 snake_case，语义单一 | `get_disk_usage` |
| REST API | 小写、资源复数、版本前缀可选 | `/api/v1/sessions` |
| 环境变量 | 全大写下划线 | `LLM_API_BASE` |

---

## 4 格式与风格

- **缩进**：项目内统一 2 或 4 空格，禁止 Tab 与空格混用。  
- **行宽**：建议 ≤ 100～120 字符（前端可按 Prettier 默认）。  
- **文件编码**：UTF-8。  
- **格式化**：前端用 Prettier/ESLint；Java 用 google-java-format 或团队选定的 Checkstyle；Python 用 Ruff/Black（择一固化）。  
- **提交前**：至少通过本地 format + lint；CI 中保持一致命令。

---

## 5 注释与文档字符串

- **必须注释**：安全规则、风险分级、与 OS 交互的副作用、非显而易见的并发与时序。  
- **避免废话**：不要复述代码字面含义。  
- **公开 API**（HTTP、MCP tool、SDK）：用 OpenAPI / JSON Schema / MCP 工具描述写清楚入参、错误码、副作用。  
- **复杂流程**：在 `docs/` 或模块内 `README.md` 用步骤或序列图说明，代码里用简短块注释指向文档路径。

---

## 6 日志规范

- **级别**：ERROR / WARN / INFO / DEBUG；生产默认 INFO。  
- **结构化**：优先 JSON 或键值对，字段至少包含：`timestamp`、`level`、`traceId`、`sessionId`、`module`、`event`、`message`。  
- **禁止**：打印完整密钥、用户口令、完整证书私钥、未脱敏的模型 API Key。  
- **审计日志**：与业务日志分离存储或至少分表/分 topic，便于合规导出。

---

## 7 错误处理与返回值

- **对外 API**：统一错误体，例如 `{ "code": "TOOL_TIMEOUT", "message": "...", "traceId": "..." }`，HTTP 状态码与业务码语义一致。  
- **MCP Tool**：失败时返回明确 `error` 字段，不吞异常；禁止用模糊字符串掩盖真实原因（开发环境可详细，生产可对用户脱敏）。  
- **禁止**空的 `catch`；捕获后须记录日志或向上转换为可观测错误。

---

## 8 安全编码要求（本赛题强制相关）

1. **命令执行**：优先白名单命令 + 参数化；禁止 `shell=True` 拼接未校验用户字符串；路径规范化防 `../`。  
2. **工具幂等**：文档中声明；重复调用不放大损害（读多写少、写前备份策略在设计中写明）。  
3. **权限**：业务进程默认非 root；提权路径单独模块、可审计、可关闭。  
4. **注入**：对用户输入与模型输出分别做策略校验；系统 prompt 与用户内容分隔存储与日志标记。  
5. **依赖**：固定版本或锁文件；定期关注 CVE；禁止引入无许可证或不明来源依赖。  
6. **配置**：敏感项只来自环境变量或密钥管理服务，不写死在仓库。

---

## 9 MCP 与 Agent 相关约定

- **单一职责**：每个 tool 只做一件事；组合编排放在 Agent 层而非巨型 tool。  
- **契约稳定**：tool 的输入输出 Schema 变更必须同步版本号与《软件功能设计文档》工具表。  
- **超时与取消**：每个 tool 设超时；支持上层取消时优雅结束子进程。  
- **副作用声明**：每个 tool 在元数据中标注 `readOnly` / `mutating` / `riskLevel`，供护栏使用。

---

## 10 测试要求（与代码质量绑定）

- **单元测试**：护栏规则、参数校验、路径解析、风险分级等纯逻辑必须有测试。  
- **集成测试**：可选，对关键 MCP tool 使用 mock 进程或容器。  
- **安全用例**：维护一组 Prompt 注入、越权指令样本，在 CI 或脚本中定期跑（可标记为慢测）。  
- **命名**：测试名体现场景，如 `shouldRejectRmRfOnEtc`。

---

## 11 Git 与协作

- **分支**：`main`/`develop` + `feature/*`、`fix/*`；禁止 force push 公共主分支（按校队/大赛规定执行）。  
- **提交信息**：中文或英文择一统一；格式建议：`类型: 简述`，如 `feat: 增加磁盘感知 MCP`、`fix: 修复意图校验误判`。  
- **Code Review**：涉及安全、权限、执行路径的改动至少一人复审。

---

## 12 性能与资源

- 限制模型上下文长度与历史轮数；大结果分页或摘要后入模。  
- 采集类 tool 注意频率，避免对生产节点造成明显负载；必要时加缓存与去抖。

---

## 13 附：语言速查（按需裁剪）

### 13.1 TypeScript / 前端

- `strict` 打开；避免 `any`；异步用 `async/await` 并处理 rejection。  
- 组件不宜过大；副作用集中在 hooks/service。

### 13.2 Java

- 包名全小写；Controller 薄、Service 承载业务；异常分层。  
- 使用构造器注入；避免在静态块里做网络 IO。

### 13.3 Python

- 类型标注逐步补齐；`src` 布局；虚拟环境锁定依赖。  
- 子进程用明确参数列表，避免字符串 shell。
